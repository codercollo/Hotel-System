~~~~ implementation / development plan ~~~~

## Phase 0 — Platform Bootstrapping (No business logic)

**Objective:** The entire stack runs locally with a single command.

### Scope

* Dockerized services for:

  * PostgreSQL
  * Redis
  * RabbitMQ
  * Backend API
  * Frontend (Nuxt)
* Working `.env.example` for both applications
* `make dev` (or equivalent) starts the full stack
* Database migrations execute successfully
* Backend health endpoint responds
* Nuxt application loads in the browser

### Deliverables

* Functional `docker-compose.yml`
* Verified environment configuration
* Working migrations pipeline
* Health endpoint available at `/api/health`
* Frontend reachable and rendering

**Outcome:** A running platform with no features, ready for backend and frontend development.

---

## Phase 1 — Core Backend Infrastructure (Foundation Layer)

**Objective:** Implement all cross-cutting backend primitives before any domain logic.

### Scope (only these areas)

* `pkg/` utilities: error handling, responses, logging, JWT, validation, pagination, cache, ID generation
* `middleware/`: authentication, RBAC, logging, CORS, recovery, request ID
* `database/`: pgx pool initialization and migration runner
* `config/`: environment configuration loader
* `events/`: broker interface and in-memory implementation

### Deliverables

* Structured JSON success/error responses
* Centralized error types mapped to HTTP responses
* JWT creation and validation utilities
* Middleware chain operational
* Database connection pool verified
* In-memory event bus usable in tests
* A basic integration test hitting a dummy route

**Outcome:** The backend plumbing is complete and safe for module development.

---

## Phase 2 — Identity Layer (Auth, Users, Roles)

**Objective:** Establish authentication, authorization, and RBAC for the entire system.

### Backend Modules

* `internal/auth`
* `internal/users`
* `internal/roles`

### Frontend Pages

* `/auth/login`
* `/auth/register`

### Deliverables

* Register, login, refresh token flows
* JWT middleware attaching user to request context
* RBAC middleware enforcing permissions
* Seed script creating default admin and user roles
* Frontend login flow storing and using tokens
* Verified protected routes

**Outcome:** System-wide identity and permission enforcement.

---

## Phase 3 — Items Module (First Domain Implementation)

**Objective:** Establish the reference pattern for all domain modules.

### Scope

* `internal/items`
* Admin items management page
* Public items listing and detail pages

### Deliverables

* Admin CRUD for items
* Public item listing and detail views
* PostgreSQL full-text search
* Image upload using local storage stub
* Unit tests for service and handlers

**Outcome:** Proof that clean architecture and module boundaries work in practice.

---

## Phase 4 — Orders Module (First Cross-Module Workflow)

**Objective:** Connect multiple modules into a business workflow.

### Scope

* `internal/orders`
* Orders pages in frontend
* Cart store activation

### Deliverables

* Create order from items
* Order status lifecycle
* Order history view
* Integration test: user → order → database

**Outcome:** Validated cross-module orchestration.

---

## Phase 5 — Payments Module (External Integration)

**Objective:** Integrate with external payment providers and validate event-driven flow.

### Scope

* `internal/payments`
* Implement one provider initially (e.g., M-Pesa)
* Webhook verification using shared crypto utilities

### Deliverables

* Initiate payment for an order
* Webhook updates payment status
* Order status updated via payment event
* Integration tests with mocked provider

**Outcome:** External IO and event-driven updates proven.

---

## Phase 6 — Notifications, Events, and Worker Process

**Objective:** Make the asynchronous worker meaningful.

### Scope

* `internal/notifications`
* `events/handlers/*`
* `cmd/worker`

### Deliverables

Triggered by order confirmation:

* Email notification sent
* In-app notification stored
* WebSocket push to connected clients

**Outcome:** Asynchronous architecture validated.

---

## Phase 7 — Uploads (Storage Abstraction)

**Objective:** Promote file handling to a first-class capability.

### Deliverables

* Signed URL upload flow
* Proper storage and retrieval of item images
* Storage interface validated with local and S3 implementations

**Outcome:** Storage abstraction ready for production use.

---

## Phase 8 — Search Abstraction

**Objective:** Decouple search implementation from the application.

### Deliverables

* `SearchRepo` abstraction verified
* Items searchable from the frontend
* Ability to swap PostgreSQL search with Elasticsearch later without refactoring

**Outcome:** Search engine independence.

---

## Phase 9 — WebSockets (Real-Time UX)

**Objective:** Enable real-time user experience.

### Deliverables

* Live notification updates
* Real-time order status updates

**Outcome:** Functional WebSocket layer integrated with events.

---

## Phase 10 — Admin Module

**Objective:** Provide operational control and visibility.

### Deliverables

* Admin dashboard with statistics
* Management interfaces for users, roles, items, and orders

**Outcome:** Administrative control over the platform.

---

## Phase 11 — Test Hardening

**Objective:** Increase system reliability through comprehensive testing.

### Deliverables

* Integration tests for auth, orders, and payments
* Mock repositories and providers
* In-memory event broker used in tests

**Outcome:** Confidence in system behavior and regression safety.

---

## Phase 12 — Production Hardening

**Objective:** Prepare the system for production deployment.

### Deliverables

* `docker-compose.prod.yml`
* Rate limiting and CORS configuration
* Structured logging and request IDs
* Health checks
* Seed scripts
* Backup strategy

**Outcome:** Production-ready platform.

---

## Dependency Rationale

Each phase unlocks the next:

| Phase                         | Enables                              |
| ----------------------------- | ------------------------------------ |
| Platform bootstrapping        | Local development environment        |
| Core infrastructure           | Safe module development              |
| Identity layer                | System-wide security                 |
| Items                         | Domain implementation pattern        |
| Orders                        | Cross-module workflow                |
| Payments                      | External integration and events      |
| Notifications                 | Worker usefulness                    |
| Uploads, Search, WebSockets   | Platform maturity                    |
| Admin                         | Operational control                  |
| Testing, Production hardening | Reliability and deployment readiness |

---

## Execution Rule

* Do not develop modules in parallel.
* Complete each phase fully before proceeding to the next.
